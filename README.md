# 可信交易确认方案（网银木马防御演示）

> 威胁模型：**用户电脑完全不可信**。木马可以改页面 DOM、劫持请求、替换二维码、伪造成功页、做相似户名社工。
> 目标：用户在**手机**上看到并确认银行服务器**真正会执行**的收款方与金额；上述任何攻击都不能让一笔未被用户在手机上真实确认的交易被执行。

## 一、安全架构

```
┌─────────────────────┐        ① 发起交易（数据可被木马篡改，无所谓）
│  中毒电脑 · 网页端   │ ───────────────────────────────┐
│  （信任等级：零）     │                                 ▼
│  木马：DOM/fetch/二维码 │                    ┌──────────────────────┐
└─────────────────────┘                     │  银行服务器（权威）     │
                                            │  - 交易唯一权威来源     │
┌─────────────────────┐   ② 独立通道直连     │  - CoP 户名校验        │
│  手机 App（信任锚）  │ ◄──────────────────► │  - 风险引擎            │
│  - 设备密钥存安全区   │   ③ 服务器签名数据    │  - Ed25519 验签后执行  │
│  - 验服务器签名       │   ④ 设备密钥签名确认  └──────────────────────┘
└─────────────────────┘
```

两条信任原则：

1. **数据路径不经过电脑**：手机通过独立网络通道直接向服务器拉取交易，展示的是服务器记录而非网页回传。
2. **执行必须有设备签名**：服务器只认手机安全区（iOS Keychain / Android Keystore）里 Ed25519 私钥的签名，签名消息是规范化交易体的哈希。电脑端没有也不可能拿到这把私钥。

### 签名与防重放

- 签名消息带域分隔前缀：`BANK-CONFIRM:v1:single:<txHash>` / `BANK-CONFIRM:v1:batch:<txHash>`，拒绝用另一套前缀。
- 交易终结（executed/rejected）后服务器拒绝任何重复确认。
- 手机端展示前先验证服务器对 `txHash` 的 Ed25519 签名，验签失败直接阻断 UI。

### 批量代发（120 笔）怎么签得过来

- **Merkle 承诺**：服务器对全部明细建 Merkle 树，`txHash` 覆盖 `merkleRoot`；手机端本地重算根并比对，改任意一行根就变、签名即失效。手机还可对任意一行向服务器索取包含证明（inclusion proof）独立验证。
- **风险分层**：120 行不全丢给用户。引擎标出高风险（新账号、账号与上月不同、户名校验失败、重复账号、金额异动 ≥30%）与中风险，默认只审阅风险行，正常行折叠。
- **人读摘要**：总笔数、总额（含人民币大写）、较上月差额、新账号/变动/重复计数，一眼看懂批次全貌。
- **高危二次核验**：高风险批次需手动输入总金额 6 位数字，防"看都不看就点确认"。

## 二、六种模拟攻击与防御点

| # | 攻击 | 木马动作 | 为什么失败 |
|---|------|---------|-----------|
| ① | 页面显示掉包 | 提交后把网页收款账号改回"正确"值 | 手机展示服务器记录的真实账号，与网页无关 |
| ② | 请求报文掉包 | 劫持 fetch 改收款账号为攻击者账号 | 服务器按被改账号建交易；手机显示真实收款方+新户/户名高危，用户拒绝 |
| ③ | 二维码替换 | 换掉确认二维码内嵌编号 | 手机以服务器待确认列表为准，扫码只是入口，不参与信任决策 |
| ④ | 相似户名社工 | 换成"北京云海科技有限责任公司"（多"责任"二字） | CoP 户名校验 + 新收款人高危标记，账号本身也不同 |
| ⑤ | 批量单篡改 | 120 行中只改第 37 行账号与金额 | 风险引擎逐行定位该行；Merkle 根变化；摘要出现新账号计数 |
| ⑥ | 伪造成功页 | 拒绝后网页显示"转账成功"假回单 | 资金实际未划转；手机与服务器真实状态为 rejected，假页面无签名回单 |

## 三、目录结构

```
packages/core/     共享 TypeScript：Ed25519、规范化哈希、Merkle 树、人民币大写、风险引擎、身份方块
server/            Express 银行服务器：交易权威、CoP、风控、SSE 推送、设备验签与执行
web/               中毒电脑网银（React）：木马控制台 + 6 种攻击 + 业务页面
mobile/            可信手机 App（React，手机外壳样式）：独立通道、验签、分层审阅、签名确认
scripts/e2e-smoke.ts  端到端冒烟测试（32 项断言）
```

## 四、运行

```bash
npm install
npm run dev        # 同时启动：:4000 服务器 / :5173 网页端 / :5174 手机端
```

浏览器打开：

- 电脑端（中毒）：http://localhost:5173
- 手机端（可信）：http://localhost:5174

其他命令：

```bash
npm test           # core 单元测试（20 项）
npx tsx scripts/e2e-smoke.ts   # 端到端攻防链路（需先启动服务器）
npm run typecheck  # 四个工程全量类型检查
```

## 五、演示脚本（建议顺序）

1. **正常基线**：所有攻击关闭 → 网页发起单笔 → 手机端核对（身份方块、账号分组、大写金额、视觉哈希）→ 三项核对打勾 → 长按签名 → 交易执行、网页状态同步。
2. **攻击②报文掉包**：武装"请求报文掉包" → 同样发起 → 观察木马日志 → 手机端出现陌生收款人"陈志强"、新收款人+户名高危 → 输入账号末 6 位后仍可拒绝 → 网页显示 rejected。
3. **攻击①+⑥**：再开"页面显示掉包""伪造成功页" → 发起并在手机拒绝 → 网页回显仍是原公司账号、还弹出假"转账成功" → 对照手机端真实状态。
4. **攻击④相似户名**：武装后发起 → 手机端 CoP 警示与新户标记，两个名字逐字对比。
5. **攻击⑤批量篡改**：切到批量代发 → 武装后提交 → 手机端摘要显示新账号计数，风险行列表直接定位第 37 行 → 展开可验 Merkle 包含证明 → 整批拒绝。
6. **干净批次**：关闭攻击提交 120 笔 → 手机端重算 Merkle 根一致、无高风险 → 签名确认整批执行。

## 六、手机确认页的防误判设计

- **身份方块（identicon）**：同一账号图案恒定，换账号图案立刻变，靠视觉记忆发现掉包。
- **账号四位分组 + 逐位核对按钮**：强制用户对账号、金额、户名分别确认。
- **金额大写**：数字与中文大写双呈现，防形似数字（8/0、1/7）蒙混。
- **CoP 户名校验**：银行核心系统返回账号实名，申请户名不一致直接红色阻断框。
- **高危硬门槛**：高危交易必须手动输入账号末 6 位，证明人确实在读手机屏幕。
- **长按 1.2 秒签名**：防误触、防点击劫持，签名动作有明确的物理意图。
- **视觉哈希词组**：完整哈希折叠成 6 个中文词组，可在网页与手机间肉眼交叉比对。

## 七、演示环境与真实系统的差距

| 演示做法 | 生产环境对应 |
|---------|-------------|
| 设备私钥存 localStorage | iOS Keychain / Android Keystore（StrongBox），私钥不可导出 |
| 服务器公钥由接口下发 | App 预置公钥 + TLS 证书绑定（pinning），首次信任不可被网络替换 |
| 单台服务器内存存储 | 核心账务系统 + HSM/KMS 签名，交易落库与对账 |
| 木马在同页 JS 内劫持 fetch | 真实木马为注入进程/钩子/BHO，攻击效果等价，防御不依赖网页干净 |
| 无登录与授权 | 设备绑定、生物识别、交易限额、多设备管理与吊销 |
